Success looks like: an admin can authorize Miro on MSPbots Connector and an AI agent can then read and make simple edits to that user's Miro boards (sticky notes, cards) through the standard MCP tool-calling interface.

## Product design

### Goals / Non-goals

**Goals**

- Give MSPbots Agent-platform users (and any MCP-compatible AI client, per the ticket's own wording) the ability to connect their own Miro account and let an AI agent read board contents and make a bounded set of edits (create/update/delete sticky notes and cards; read other item types), through the standard MCP tool-calling contract (`initialize` → `tools/list` → `tools/call`).
- Keep the connector stateless and per-request, matching every other connector on the platform: this service never stores a Miro credential; every call carries the caller's own Miro access token in a request header, and one request's token/data is never visible to another concurrent request.

**Non-goals (first version)** — none of these were asked for in the ticket, and none require a product decision; they are DEV01's own scope calls for a first version (see "Decisions made by DEV01" below), not blocking Open Questions:

- Miro's Enterprise-tier resources: organizations, teams, projects.
- Webhooks — this service has no public callback endpoint to receive them, and nothing in the ticket asks for push/event notifications.
- Miro's visual "connector" item type (arrows/lines between items) and board tags — low value for a text-oriented agent in a first version.
- Board templates, duplication, or any board-creation option beyond a plain new board.
- Any UI for Miro's OAuth2 interactive authorization flow — out of scope for this MCP server itself. The server only ever receives an already-issued Miro access token via request header; how that token was obtained (a Miro "service account" token, or a platform-brokered OAuth flow) is a platform/gateway concern, consistent with how `connect.mspbots.ai` already describes "authorize on each vendor's own page" / "bring your own API keys" for other connectors (see `chargebee-mcp` README, "Why Connector" section).

### Acceptance criteria

- **AC1**: Given a request to the miro-mcp server carries a valid Miro access token in the `X-Miro-Access-Token` header, When the caller sends `tools/list`, Then the response lists the Miro tools (board discovery, item read/write, members) with no error.
- **AC2**: Given a request carries no `X-Miro-Access-Token` header (or an empty one), When any tool is called, Then the server returns a structured 401 error naming the missing header, and no outbound call is made to Miro's API.
- **AC3**: Given a valid token, When the caller invokes `miro_list_boards` (optionally with a search term), Then the response is a bounded list (default ≤50, hard cap ≤200) of boards visible to that token, each with id/name/url, plus a pagination cursor if more exist; an account with no boards gets back an empty list, not an error.
- **AC4**: Given a valid token and a `board_id`, When the caller invokes `miro_get_board`, Then the response returns that board's details, or a structured `not_found` error if the `board_id` does not exist or is not accessible to this token.
- **AC5**: Given a valid token, When the caller invokes `miro_create_board` with a name, Then a new board is created in Miro and its id/name/url are returned.
- **AC6**: Given a valid token and an existing `board_id`, When the caller invokes `miro_list_board_items` (optionally filtered by item type), Then the response returns a bounded, paginated list of items on that board.
- **AC7**: Given a valid token, `board_id` and `item_id`, When the caller invokes `miro_get_item`, Then the response returns that item's details, or a structured `not_found` error if the item does not exist on that board.
- **AC8**: Given a valid token and `board_id`, When the caller invokes `miro_create_sticky_note` with text content (and optional position/color), Then a sticky-note item is created on that board and its id is returned.
- **AC9**: Given a valid token and `board_id`, When the caller invokes `miro_create_card` with a title (and optional description/position), Then a card item is created on that board and its id is returned.
- **AC10**: Given a valid token, `board_id` and `item_id`, When the caller invokes `miro_update_item` with new content/position, Then the corresponding item is updated in Miro, or a structured `invalid_argument`/`not_found` error if the field is not valid for that item's type or the item does not exist.
- **AC11**: Given a valid token, `board_id` and an explicit `item_id`, When the caller invokes `miro_delete_item`, Then that single item is permanently removed from the board; the tool accepts exactly one explicit id per call (no bulk/fuzzy delete), is annotated `destructiveHint: true`, and deleting an id that does not exist returns `not_found` rather than a silent success.
- **AC12**: Given a valid token and `board_id`, When the caller invokes `miro_list_board_members`, Then the response returns the board's collaborators (id, name, role), bounded and paginated like other list tools.
- **AC13**: Given Miro's API returns a rate-limit (429) or an upstream 5xx for any tool call, Then the MCP server returns a structured error with code `rate_limited` or `upstream_error` and `retryable: true` — never a raw exception or a bare 500 from this service.
- **AC14**: Given two concurrent requests carrying two different callers' tokens arrive at the same server process, Then neither request's Miro token nor response data is ever observable by the other (per-request isolation baseline, required of every MCP on this platform).
- **AC15**: Given a tool call's result would exceed this service's response size cap (e.g. `miro_list_board_items` on a board with hundreds of items), Then the response is truncated with an explicit pagination signal (`has_more` / cursor), never silently dropped with no indication more data exists.

## Tech design

### Conclusion

Build the first version of `miro-mcp` from scratch on the existing empty-scaffold repository: a Python 3.12 + uv + FastMCP Streamable-HTTP server, following the same structural and contract conventions already established by `chargebee-mcp` in this org, wrapping Miro's public REST API v2. Ten tools across three resource groups (boards, board items, board members), single-header bearer-token credential, structured error envelope, request-scoped isolation via `contextvars`. No product open question blocks starting work; everything above is a DEV01 scope call for the first version, recorded below.

### Where the current implementation lives

Nothing exists yet. `MSPbotsAIFramework/miro-mcp@main` (`4e82ac8`) is `README.md` only — this is a from-scratch build (SOP "main line A"), not a modification of existing code.

### Option analysis

- **Wrap Miro's REST API v2 directly (chosen)** — Miro's REST API v2 is public, stable, free, and covers every capability this ticket needs (boards, items, members). No evaluation of a pre-built alternative is needed because none exists in this org (precedent: `chargebee-mcp`'s README documents evaluating Chargebee's own official MCP server and rejecting it as read-only/incomplete before wrapping the REST API directly — the same situation does not apply here since Miro has no competing first-party MCP server mentioned anywhere in scope for this ticket).
- **Mirror every Miro REST endpoint 1:1 as a tool (rejected)** — Miro's full API surface (10+ item subtypes with per-type CRUD, org/team/project admin, webhooks, tags, visual connectors) would produce 30+ tools, violating SOP §2's "tools are capabilities, not endpoint mirrors" and the ≤20 tool ceiling. Rejected in favor of a trimmed, capability-oriented set (next section), the same reduction pattern `chargebee-mcp` used (its README documents trimming from 30 candidate tools to 10 core ones).
- **One generic `miro_create_item(type, ...)` tool instead of per-type create tools (rejected)** — a single polymorphic create tool would need a wide, type-conditional parameter schema (sticky-note style/shape fields vs. card title/description fields are unrelated), which is harder for an agent to call correctly than two narrow, well-described tools. Sticky notes and cards are Miro's two most common agent-authored content types, so they get dedicated `miro_create_sticky_note` / `miro_create_card` tools; every other item type is read/update/delete-only through the generic `miro_get_item` / `miro_update_item` / `miro_delete_item` tools (consistent with SOP §2's "merge overlapping tools" guidance applied in the other direction: split only where the parameter shapes are genuinely different).

### Data & API contract

**Base URL**: `https://api.miro.com/v2` (Miro's stable, documented REST API v2 base).
**Upstream auth**: `Authorization: Bearer <token>` per request, where `<token>` is exactly the value the caller supplied in `X-Miro-Access-Token` — this service never exchanges, refreshes, or stores a token.

**This service's own credential header**:

| Header | Type | Required | Description |
|---|---|---|---|
| `X-Miro-Access-Token` | string | Yes | A Miro OAuth2 access token or service-account access token, scoped to the boards the caller wants an agent to reach. Obtained from the Miro app the account's Developer Team created (`developers.miro.com`), or brokered by the platform's own OAuth flow for this connector. |

Missing or empty → 401, JSON body:
```json
{"error": "Missing credentials", "message": "Requires the X-Miro-Access-Token header", "required_headers": ["X-Miro-Access-Token"]}
```
(same shape as `chargebee_mcp/server.py`'s `GatewayTokenMiddleware` response, field names kept identical across MCPs in this org on purpose.)

**Tool → upstream endpoint mapping** (methods/paths per Miro's public REST API v2 reference; exact query/body field names to be pinned against Miro's OpenAPI spec during implementation — the resource shape itself is confirmed, see Current state):

| Tool | Upstream | Notes |
|---|---|---|
| `miro_list_boards` | `GET /boards` | `team_id`, free-text `query`, `limit` (capped ≤200 at this service's boundary even if Miro allows more), `cursor` passthrough |
| `miro_get_board` | `GET /boards/{board_id}` | 404 from Miro → `not_found` |
| `miro_create_board` | `POST /boards` | body: `name`, optional `description` |
| `miro_list_board_items` | `GET /boards/{board_id}/items` | optional `type` filter, `limit`, `cursor` passthrough |
| `miro_get_item` | `GET /boards/{board_id}/items/{item_id}` | 404 → `not_found` |
| `miro_create_sticky_note` | `POST /boards/{board_id}/sticky_notes` | body: `data.content`, optional `data.shape`, `style.fillColor`, `position` |
| `miro_create_card` | `POST /boards/{board_id}/cards` | body: `data.title`, optional `data.description`, `position` |
| `miro_update_item` | `PATCH /boards/{board_id}/items/{item_id}` (or the item-type-specific PATCH endpoint, if the generic one does not accept content fields for that type — confirmed at implementation time against the spec) | invalid field for the item's actual type → `invalid_argument`, not a raw Miro error passthrough |
| `miro_delete_item` | `DELETE /boards/{board_id}/items/{item_id}` | exactly one explicit `item_id`; no bulk form is exposed |
| `miro_list_board_members` | `GET /boards/{board_id}/members` | `limit`, `cursor` passthrough |

**Pagination**: Miro's v2 list endpoints already return an opaque `cursor` field for the next page (unlike `chargebee-mcp`'s PRD-17977 situation, which needed a codec to paper over a compound non-opaque cursor) — this service passes Miro's `cursor` straight through in both directions, no re-encoding needed. Every list tool enforces `limit` ≤200 regardless of what the caller requests, and truncates the response body to this service's own size cap (≤20000 chars, compact JSON, no `indent=2`) with `has_more`/`cursor` set if the true result is bigger than what was returned.

**Error envelope** (uniform across all ten tools, returned as the tool's string result, never raised as an exception):
```json
{"error": {"code": "not_found", "message": "Board abc123 not found or not accessible with this token", "retryable": false}}
```
`code` ∈ `not_configured | unauthorized | not_found | invalid_argument | rate_limited | upstream_error`; `retryable: true` only for `rate_limited`/`upstream_error`.

**Backward compatibility**: not applicable — first version, nothing to stay compatible with.

### Key flow / sequence

1. Caller sends `POST /mcp` with `X-Miro-Access-Token: <token>` and a `tools/call` body (e.g. `miro_create_sticky_note`).
2. `GatewayTokenMiddleware` reads the header; missing → 401 short-circuit (step 5 never runs); present → sets the per-request `contextvars.ContextVar`.
3. The tool handler resolves a `MiroClient` from the context, builds the Miro request (`POST /boards/{board_id}/sticky_notes`), applies the shared timeout/retry policy.
4. Miro's response is mapped: 2xx → success payload (compact JSON, capped); 4xx (not the generic ones already special-cased, e.g. 400/404) → `invalid_argument`/`not_found`; 429 → `rate_limited` (`retryable: true`); 5xx → `upstream_error` (`retryable: true`).
5. Middleware resets the contextvar in a `finally` block regardless of outcome, so the next request on the same process starts clean.

### Non-functional

- **Idempotency/concurrency**: reads (`list`/`get`) are naturally idempotent. `miro_create_*` tools are not idempotent (each call creates a new item/board) — this matches Miro's own API and is called out in each tool's description so an agent does not assume safe retries. `miro_update_item`/`miro_delete_item` are idempotent at the HTTP level (PATCH/DELETE on the same id).
- **Performance**: outbound connect/read timeouts 5s/30s; single retry with backoff on 429/5xx respecting `Retry-After`; total time per tool call capped under 120s; one `httpx.AsyncClient` per request, not shared across requests (no connection-pool-driven cross-request state).
- **Security**: credential read only from `X-Miro-Access-Token`, never logged, never persisted to disk/env; `gitleaks detect` run before delivery; repository stays private.
- **Multi-tenant isolation**: every credential and every upstream response lives in a `contextvars.ContextVar` scoped to the request's asyncio task, reset in a `finally` block — the same mechanism already proven in `chargebee-mcp` (`server.py:19-21`, `:40-88`) to prevent one caller's data/token from leaking into another concurrent request. No module-level or global mutable state holds a credential or tenant's data at any point.
- **Observability**: standard container stdout/stderr logging; no request bodies containing the credential header are logged; 429/5xx responses from Miro are logged at warn level with the upstream status code (not the credential).

Below the "must split" threshold (5) in any case.

### Risks & dependencies

- **Risk**: a few upstream field names (noted above) are confirmed-by-resource-model but not confirmed-by-exact-schema. Mitigation: implementation-time check against Miro's OpenAPI reference before finalizing `tools/items.py`'s request bodies; covered by the one manual real-account test case.
- **Risk**: Miro's rate limits are not yet measured against this org's expected call volume. Mitigation: the retry/backoff policy already respects `Retry-After`; no capacity assumption is baked into the design beyond that.
- **Dependency**: none on another ticket or another repository. This is a standalone new connector.
- **Decisions made by DEV01** (SOP 2.4, first-version scope calls with no one to ask — not product Open Questions):
  - Single bearer-token header (`X-Miro-Access-Token`) rather than separate client-id/secret/redirect-fields — because this server never performs the OAuth2 exchange itself, it only ever receives an already-issued access token (alternative considered: exposing the full OAuth2 authorization-code flow through this service's own endpoints; rejected as out of scope for a stateless per-request MCP and inconsistent with how other connectors in this org receive credentials).
  - Ten tools covering boards + the two most agent-relevant item types (sticky notes, cards) plus generic read/update/delete for every other item type, rather than one tool per Miro item subtype (alternative: ~20+ type-specific tools mirroring every Miro item type; rejected — exceeds the ≤20 ceiling and duplicates near-identical CRUD shapes for marginal benefit).
  - Tags, visual "connectors", Enterprise org/team/project management, and webhooks excluded from v1 (alternative: implement all of Miro's resource groups up front; rejected as scope inflation with no corresponding ask in the ticket — see Non-goals/OQ1).
  - Pagination passes Miro's own opaque cursor straight through with no re-encoding (alternative: wrap it in this service's own opaque cursor envelope, as `chargebee-mcp` had to do for a Chargebee-specific pagination quirk; rejected as unnecessary complexity — Miro's cursor is already opaque and resource-scoped by Miro itself).
